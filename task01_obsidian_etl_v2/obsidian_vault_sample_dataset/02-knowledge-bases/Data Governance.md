# What is Data Governance / Database Governance  - Five Aspects
資料治理 / 資料庫治理在治理資料庫的架構與運作效益，目標在於確保資料==**品質 (完整與可靠)**==、==**安全性**==與==**一致性**==的一系列實踐。設定資料庫主要著重在五個面向：收集、儲存、整合、管理 (含歸檔、銷毀)、使用。
- **收集**：資料從哪取得 (API、web、other database….)? 如何有效率地取得 (manual key-in、web scraping、automatic processes by IoT、)?
- **儲存**：放在哪裡(ERP、資料庫、NAS、地端雲端、檔案室)? 用什麼技術存放(關聯式資料庫、MongoDB、DataLake、DataWarehouse、紙本)?
- **整合**：存好資料後，如何整治這些取自於不同來源、不同系統的資料? 是否要轉換、清洗? 如何執行轉換與清洗? ==資料清洗 (ETL/ELT) 最耗時間的通常在這裡，且有可能清洗前與清洗後是需要分別設計儲存的流程。==
- **管理**：資料整合後，如何管理閱讀權限、修改權限、備份頻率、維護資料的品質? 若有過時或需求量低的資料，要怎麼規範歸檔或是刪除的流程?
- **使用**：受管理的資料，最終目的可能是用來分析、視覺化以爲公司創造最大商業價值。所以使用層面需要注意是否需要有資料目錄來協助用戶發現資料與高效利用。
## 好的資料治理流程所追求的是有效率地引入可靠的數據，有條理的彙整但不失可擴展性。
1. **可靠性**：資料完整性DI、不重複，在初始規劃資料的治理流程時，應要注意資料的：
	- 準確性：資料能反映真實狀況
	- **一致性**：數據在不同來源或不同時間點上保持一樣
	- **完整性**：數據是否能包含所有所需元素
	- 即時性：是否是最新的資料。
	- **安全**措施：各資料表治理的權責範圍與部門責任，部分參考[[個人與企業數位資產防護指南]] 或 [ISO 27001](https://www.bureauveritas.com.tw/insight/ISO27001-42001)。
2. **效率**：減少空間浪費、方便查詢
	- 好的效率需要搭配定期監督資料治理成效、確保制定出來的治理流程有效被遵循與執行。
3. **可擴展性**：觀望未來業務需求
	- 達到良好的可擴展性應要注意資料表之間的關聯
	- 存有資產目錄來登記所有資料資產

# 資料管理流程要怎麼設計
1. 遵循資料治理的流程五大面向 (收集、存儲、整合、管理、使用) 擬定資料治理的策略，在可靠性、查詢效率、可擴充性之間達到平衡。
	- 然而，我們身處數據量增長速度極快的現代，我們可能先訂好了一套資料治理流程，實際上可能會碰到記憶體、硬碟規格向上擴充速度不見得支撐得了數據的增長速度，何況硬體優化的成本也不斐，為了減緩資料寫入儲存的負擔、單機故障造成資料無法使用，以分散式儲存來管理資料的理論油然而生，詳見 [[20260421 CAP 理論]]。
2. 管理的方式就是將制定出來的治理策略實踐於整個資料的生命週期，也就是從資料誕生到消亡的歷程中都要根據治理策略來實施與維護。
3. 我們可以將管理管理流程進行模組化。例如：資料在她的生命週期裡，會需要經過創建、儲存、歸檔、刪除，==每個階段可以套用各用專屬模組處理==，如果是清洗步驟，清洗模組可應用於多個資料來源。降低錯誤並加速迭代。好處是便於團隊分工與重複使用，清洗模組可應用於多個資料來源。

# 資料清理
一些資料清理的方式
1. 缺失值：
	- 刪除缺失值：使用pandas.dropna()但要注意造成資料遺失或是失去統計意義。
	- 插補法-填補缺失值：用其他變量來填補缺失值，例如：前一個時間紀錄點溫度為26度、後一個時間紀錄點為28度，則缺失的中間時間點可以用27度填補，這種屬於插補法中的線性填補法(內插法)。通常可動用pandas.interpolate(method = 'linear')。
	- 模型預測填補缺失值：為其他變量做出統計模型，預測缺失值。例如：某一棟房屋的屋齡資料遺失了，我們根據他周遭房屋的建造年份、面積、位置來推論這棟房屋的屋齡可能為多少。
	- 多重插補：醫學研究資料中「血壓」缺失，使用MICE算法產生5組插補資料集，每次隨機考慮相關變數（如年齡、BMI），最後池化估計值提高統計穩健性。。

2. 離群值：
	- 經過統計或是資料視覺化 (box plot) 來發現離群值，接著評估這些離群值背後的形成原因是否合理，再判斷是否要刪掉、保留、或是修正。
3. 重複值：
	- 可用pandas.drop_duplicates()
4. 資料格式不一致、未標準化：
	- 將資料轉換成特性的格式。
	- 將不同度量單位轉成統一單位。
5. 其他 - 資料可靠度：
	- meta 錯位，可以清理並寫入資料庫
	- meta 缺失，不應該寫入資料庫，例如： date 缺失，不知道owner是誰，影響資料完整度。故不寫入、更不做向量化。

# 針對機器學習 (ML) 的資料治理態度
^b5d282

機器學習模型學習的資料之品質和數量，對模型成效至關重要。思考資料品質時，應著重於五個要素。
 1. 準確率：如果資料不準確，模型會學到錯誤的模式，做出錯誤的預測。想像一下，如果用一本圖片標示錯誤的書教孩子認識動物，他們就會學到錯誤的知識。AI 也是如此。
 2. 完整度：完整性是指資料集的大小，以及資料集中的代表性。資料集的大小很重要，因為模型需要足夠的資料才能做出準確的預測。如果氣象學家只根據前一天的資料預測天氣，預測結果會比使用更大樣本的預測結果差得多。
 3. 代表性：資料必須具代表性且包容多元，否則可能導致樣本偏誤和結果偏頗。如果顧客偏好資料集缺少特定客層的資訊，模型可能會對該群體做出不準確或有偏誤的概括性推論。
 4. 一致性：==資料格式或標籤不一致==，可能會讓模型混淆，進而影響學習成效。想像一下，拼圖的某些碎片標有數字，另一些標有字母，這會是一團糟。
 5. 關聯性：資料必須與 AI 的設計用途相關。舉例來說，倫敦的交通模式資料不太可能用於預測堪薩斯州的作物產量。

# 資料顆粒度
- 資料表顆粒度（Data Granularity）指的是資料表中每筆記錄所代表的資料細緻程度或最小單位，決定了資料的「粗細」層級。
- 顆粒度含義：
	- 顆粒度越細（如每日每客戶每產品），每行記錄包含越多維度細節，能支援更精準分析；顆粒度越粗（如每月總銷售額），則資料被聚合，適合高階概覽。  例如，銷售資料表若以「訂單明細」為粒度，則記錄產品名稱、數量等細項；若為「月總額」，則僅存聚合值。

- 影響什麼：
	- 不同粒度影響儲存空間、查詢效能與分析深度：細粒度資料量大、儲存成本高但靈活，可向下鑽取（drill-down）；粗粒度查詢快、空間小，但無法細分分析。
	- 在 ETL 管線中，粒度決定維度模型設計，如星型schema中事實表的行數直接受粒度控制，過細易導致效能瓶頸。
- 選擇粒度依業務需求，如交通事故分析可選「每日每路段」粒度支援Tableau儀表板細析；過粗則限製SQL查詢多維交叉。

# 資料資產目錄
1. 目的：增加數據的可發現、可信任、高度理解不誤解，有資料資產目錄將有機會達到良好的資料治理效果。
2. 資產目錄應有幾個功能：
	- (格式)能為數據欄位定義清楚：數據的欄位名稱、資料表名稱、數據格式、業務用途或是物理意義
	- (格式)經由支援關鍵字搜尋、預先給予適當的標籤，提升查詢效率。
	- (使用案例)有欄位可以接受使用者填寫回饋。
	- (位置)包含數據血緣，在目錄中將數據血緣做可視化。
	- (品質評分)附上數據品質評分卡。
	- (所有者、敏感度標籤)標示好權限與安全標籤，提醒或控管數據的敏感度。
3. 工具：Gluu、DataHub、Azure Data Catalog、AWS Glue Data Catalog。未來有用到再去擴展筆記。
